# R7RS-small準拠計画と要求追跡

GuriはR7RS-smallへの移行を計画しています。
現在の処理系は独自仕様のGuriであり、R7RS-small準拠ではありません。
このページは実装目標と判断事項を示し、現在使用できる機能は[言語仕様](https://github.com/0x6d61/guri/wiki/Language-Specification)と[関数リファレンス](https://github.com/0x6d61/guri/wiki/Functions)に記載します。

## 確定した方針

- Guri自体でアプリケーションを作成・実行する単体処理系を主用途にします。
- 起動時に標準入力、標準出力、標準エラーを使える設計とし、Guriが開いたファイルなどの資源はGuriが管理します。
- Go側で開いてGuriへ渡した資源は借用し、Guriから元の資源を閉じません。
  組み込み用APIの詳細は将来の拡張時に扱います。
- R7RS-smallを正とし、既存Guriとの後方互換性は要求しません。
- 独自データ型、独自構文、非標準の組み込み機能はいったん除去し、準拠後の拡張は別に検討します。
- 標準型の通常の内部表現は実装側へ委任済みです。利用者から見える新たな制限や公開Go API、CLIへ大きな影響を与える選択は、選択肢と影響を示してユーザーへ相談します。
- 規格で決まっている動作はその要件に従います。必須要件を省略する判断を独自仕様として通しません。

除去は、対応する標準機能への置換と同じPRで順に進めます。
現在の機能がこの計画の記載だけで削除されたことにはなりません。
標準機能を実装する各Issueで旧仕様の入口とテストを移行し、#67で残存する独自機能を監査します。

初回の証拠欄が空の行は検証済みではありません。
「検証済み」へ変更するPRには実装箇所、テスト名、使用例、規格上の制限を記録します。
既存のテスト成功だけでは、標準の構文や動作を確認した証拠になりません。

### 要件の分類

| 分類 | 扱い |
|---|---|
| 必須 | baseの公開束縛と規格の必須動作を満たす。未対応は準拠判定を失敗にする |
| 任意 | base以外のライブラリは採用の有無を記録する。採用したライブラリは公開束縛一式を実装し、追加の識別子を標準ライブラリから公開しない |
| 実装依存または実装制限 | 規格が許す範囲と根拠の節を示し、ユーザー確認後に文書化する。単なる未実装とは区別する |
| 未規定 | 規格が結果を一意に定めない。許される結果や性質を検証し、他処理系の単一の結果を必須にしない |
| エラーの検出が必須 | 「an error is signaled」に相当する条件は非継続例外を発生させ、指定された述語も検証する |
| エラーだが検出は必須でない | 「it is an error」に相当する条件は必須検出と区別する。Guriが追加で検出する契約は別に記録する |

この分類は[R7RS §1.3](https://standards.scheme.org/corrected-r7rs/r7rs-Z-H-3.html)に基づきます。
評価順や同一性の未規定部分を、現行Guriの左から右の評価などに固定して標準要件と取り違えないようにします。

## 実装順序と共有契約

[親Issue #42](https://github.com/0x6d61/guri/issues/42)の依存関係を使います。
最初は#43の台帳を整備し、#44で規格テストの実行基盤を作ります。
#45の値層を土台に、#46のReaderと#47の評価器を進めます。
その後はコア構文、衛生的マクロ、制御機能と標準手続き、入出力とライブラリを統合し、#66と#67で準拠と独自機能の除去を監査します。

作業を分担する場合は、次の契約が決まっていることを入口条件にします。

- 値の表現と同一性、Pairとコレクションの更新規則。
- 識別子と構文オブジェクト、ソース位置、展開後のCore表現。
- 手続き呼び出しと再開、複数値、例外、動的実行範囲の扱い。
- 環境の所有権と公開Go APIの詳細。ポートの借用・所有は下記の合意を適用します。

共有契約を変更するPRは、利用側のIssueとテストへの影響を列挙してからレビューします。
独立した担当が同じ型や評価器を別々に変更しません。
AIによる分担でも、ブランチ、TDD、CIと通常のmerge commitの開発フローを守ります。

## 準拠の受け入れ条件

1. 必須要求と採用した任意ライブラリを、下位要求IDから実装、unitテスト、Wikiまで追跡できること。
2. 未規定の結果、実装制限、任意機能、未対応を別々に報告し、必須機能のskip/xfailを成功として集計しないこと。
3. 外部テストはライセンスとリビジョンを固定し、ネットワークなしで再実行できること。他処理系との結果比較は規格を補助するものとして使うこと。
4. 継続の再利用、マクロの衛生、共有と循環、動的実行範囲をまたぐ結合テストがあること。
5. 末尾呼び出しの空間要件を、単なる大きな再帰回数の成功だけで判定しないこと。
6. Goのunitテスト、vetとCI、実行可能な使用例が成功し、公開Wikiが原稿と一致すること。
7. 独自構文、独自型、旧組み込みの意味が標準モードに残っていないことを#67で確認すること。

第7章の形式文法と意味論は追加の処理系機能ではなく、実装と展開を監査する資料として使います。
Appendix Aの公開束縛とAppendix Bのfeaturesを照合し、規格外の実装を「準拠」の代わりにしません。

## 単体アプリ実行の方針と資源管理の合意

ユーザーはGaucheのように、Guri自体でアプリケーションを開発・実行する立ち位置を承認しました。
追加の合意として、Go側で開いてGuriへ渡した資源は借用します。
Schemeのclose-portはポートを閉じ、必要なflushを行いますが、借用元のGo資源のCloseは呼びません。
元の資源を閉じる責任はGo側に残します。
組み込み用APIの詳細は将来の拡張時に扱い、この方針の回答待ちを理由に単体処理系のポート実装を保留しません。

単体実行では標準入力、標準出力と標準エラーを起動時に用意し、Guriが開いたファイルなどの資源を処理系で管理します。
標準入出力の接続、close、flush、例外と継続に対する動作は、R7RS-smallの要件に従って#59/#60へ実装します。
この合意を理由に、継続による脱出でcall-with-portの資源を無条件に閉じるなど、規格と異なる終了規則を追加しません。
プロセス終了とCLIへの接続は#65/#67で扱います。

ここに記載した内容は設計方針です。
公開CLIで標準ポートが既に利用可能になったことは意味しません。
実装済みの内部機構と公開CLIの適合結果を引き続き区別します。
